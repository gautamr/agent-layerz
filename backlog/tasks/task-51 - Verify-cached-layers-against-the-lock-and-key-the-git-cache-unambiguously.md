## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in the TASK-50.1 security review. contentHash is computed (src/resolve/stack.ts) but never compared with the lock when a cache entry is read. Git cache keys flatten the URL (src/resolve/sources.ts), so github:acme-corp/layer and git:https://github.com-acme-corp/layer share one key. With a lock SHA set and the entry cached, no clone runs, so a crafted repository can read another layer's cached copy if it knows that layer's commit, and a private layer can end up in its build output.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Every cache read compares the layer's content hash with layer.lock and fails the build on a mismatch, naming the layer
- [x] #2 Git cache keys are an unambiguous encoding of the source URL (for example a hash), and two different URLs never share an entry
- [x] #3 Acceptance tests cover a colliding URL pair and a tampered cache entry
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Findings: readLock already rejects a lock sha that is not 40 or 64 hex characters (src/model/lock.ts), so the sha reaches resolveGit validated; add a regression test only.
2. sources.ts: git cache key becomes git-<sha256 of the exact clone argument> (the clone URL for remote and github: sources, the canonical absolute path for local git: sources, so a relative local path in two repos never shares an entry). No other normalisation, so https and ssh forms of a host never alias. Old flat-key entries are ignored (one re-clone). ResolvedSource gains cached: true when the directory already existed (git entry read, tree@ entry read).
3. New src/resolve/cache-integrity.ts: pure verifyCachedLayer(layer, lockedEntry): ok | miss (content hash equal), and lockedEntryFor(locked, source, sha) which picks the lock entry only when the source and the resolved sha both match. loadStack calls them after loadLayer for cached reads; a miss throws FatalError naming the layer and cache dir and saying to delete that entry; no file content printed. Unpinned path: layers and fresh clones are not checked.
4. Tests: test/acceptance/28-cache-integrity.test.ts with fixtures in test/fixtures/28-cache-integrity: colliding pair (local bare repos whose old keys flatten to the same string, plus the github:/git: https pair at the key function), tampered git cache entry, tampered tree@ entry, ref bump not checked, non-hex lock sha, unit cases for verifyCachedLayer. Isolated HOME and XDG_CACHE_HOME.
5. Spec: update 5.3, 6, 7.13 (No fetch), the 7 lead-in note, 9.3 and 12 to describe the check and key format. Run test, lint, alz:check; tick ACs 1-3; AC 4 only the callable half, the fail-closed half is wired in TASK-50.2.

2026-11-22 (@implementer) review fixes. (1) BLOCKER: materializeAtRef used rev-parse <sha>:<prefix>, which returns a submodule entry's recorded id (any tree id) or a link's blob. treeAt (src/resolve/tree-cache.ts) now requires git ls-tree (cwd-relative, run from the top, --literal-pathspecs) to list the path as mode 040000 type tree; otherwise the ref is unresolvable. Acceptance test with a gitlink at the layer path. (2) tree@ entries: chosen design is to stop using git checkout-index. It applies the working repository's info/attributes, core.attributesFile, autocrlf and in-tree attributes, so the bytes could depend on a crafted repo, and in-tree eol or ident attributes would make the written bytes differ from the blob ids. Entries are now written from git cat-file --batch blobs, raw, mode 0644 or 0755 set explicitly. Consequence: in-tree attributes are no longer applied to pinned layers (deliberate: byte-identical, verifiable output), and a link inside a layer tree is now an error (the loader ignored links anyway). A path with a .git segment is refused; submodule entries are skipped. On every cached tree@ read the entry is verified against git ls-tree -r of that tree (blob id computed in process with no filters, executable bit, no extra or missing file, no link, entry itself a real directory), independent of the lock; the lock check stays as extra. Test: docs commit moves the commit but not the tree, entry tampered, build fails. Old entries written by checkout-index verified fine against this repo's real cache; an old entry containing a link or converted line endings would now fail with the delete hint. (3) Existing git entry vs fresh clone: when the clone finds the entry already present it compares content hashes, discards the clone and fails with the delete hint on a difference; a cache entry that is a link is refused. (4) loadLayer lists and hashes first, runs the cache check, then parses; the error names the layer by the lock entry's name and the source, never by parsed meta. layer.yaml must be a regular file for every layer: note that before this change a symlinked layer.yaml was followed, not refused (existsSync and readFileSync follow links), so this is a new refusal, with a test. (5) init and lint now pass readLock(cwd)?.layers; tests cover both. readLock now type-checks name, source, contentHash, sha and rev. (6) Contract for TASK-50.2 documented in the doc comments of lockedEntryFor and verifyCachedLayer and in spec 5.3 (future tense). Spec: 4.2, 5.3 (hash exclusions, mode not in the hash, every command that stops, what a malicious lock can still do), 6, 7.13 (index only for a real tree), 9.3 narrowed. Follow-ups, not done: (a) git-clone entries (git@ key) have no file-mode check, since the content hash excludes the mode and a clone entry has no tree id check; a follow-up should verify them against git ls-tree of the checked-out commit (the hash format must not change, it would invalidate every lock); (b) time of check versus use: files are read again after being hashed, so only a local writer racing the build could swap them; (c) old flat-key cache entries from before this change are never removed; (d) the clone entries still use git checkout with the user's global git config.

2026-11-22 (@implementer) second review round. Done: (1) pinned entries are now tree2@<tree>; old tree@ entries are ignored and never removed. (2) Links and inner submodule entries in a pinned tree are skipped (not written; a link in an entry is still a change), so CLAUDE.md -> AGENTS.md keeps working; tests with a committed link and gitlink. (3) verifyTreeEntry ignores .DS_Store, .git and node_modules in an entry unless the tree has them. (4) listTree refuses paths that collide after NFC and case folding (file/folder included) before any write; verifyTreeEntry compares names in NFC (HFS+ returns NFD, APFS keeps the written form; colliding names are already refused, so NFC is injective); the entry is verified in the temp dir before the rename, so the first build is checked. The NFC/NFD test sets core.precomposeunicode=false in the crafted repo because macOS git would otherwise merge the pair. (5) requireBlobs runs git cat-file --batch-check over every blob id and needs a blob, before a cached entry is trusted or one is written; GIT_NO_REPLACE_OBJECTS=1 and GIT_NO_LAZY_FETCH=1 on every git call in materializeAtRef and tree-cache; writeTree checks each blob's bytes against its id. Test: a crafted repo with the victim's tree id but none of its blobs (update-index --info-only --cacheinfo, write-tree --missing-ok), which fails and leaves the repo unchanged; I used this rather than a partial clone. Replace-ref test: a blob replaced by a ref still writes the original bytes. (6) readLock checks name against NAME_PATTERN; tree paths and sources in these errors go through quote/stripControl (src/core/sanitize.ts, new quote). (7) loadLayer hashes and runs the cache check before it requires or parses layer.yaml, so a tampered entry with layer.yaml deleted gets the cache error. ## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Cache integrity for layer sources. Git cache keys are git-<sha256 of the exact clone argument>@<sha>, so no two URLs share an entry. Pinned path: layers are cached as tree2@<tree>, written from raw blobs (no attributes or filters), refused unless the layer path is a real tree, refused unless the building repository holds every blob, verified against git ls-tree on write and on every read (blob ids, exec bit, no extra files or links, NFC names, skipped names ignored), with replace refs and lazy fetch off. Cached git reads are compared with the lock's content hash, and an existing entry with a fresh clone. layer.yaml must be a regular file and is parsed only after the cache check; errors name the layer from the lock and quote repository text. init and lint read with the lock; readLock type-checks fields and names. verifyCachedLayer and lockedEntryFor carry the fail-closed contract for TASK-50.2. Spec §4.2, §5.3, §6, §7.9, §7.13, §9.3, §12. Tests: 28-cache-integrity (42); 177 passed, 1 skipped; lint and alz:check clean. Reviewed in three rounds by reviewer and security-reviewer, both ready. Breaking (0.x) changes and follow-ups are in the notes.
